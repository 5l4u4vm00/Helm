# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Helm (package name `helm`) is a Tauri 2 + React 19 + TypeScript desktop terminal application. Its core feature is "agent awareness": each session is a PTY, and the frontend passively scans terminal output to detect the running CLI agent (Claude Code, Codex, etc.), derive its state (thinking / tool / waiting / done / error), and centrally surface pending approval prompts, cost/token usage, and file changes. It supports tmux-style split views.

> Comments and commit messages are written in English; code follows the naming and style conventions in `~/.claude/CLAUDE.md`.

## Common Commands

```bash
npm run tauri dev      # Development (runs vite + tauri together; use this to run the actual app)
npm run dev            # vite only (browser-only, no PTY; for quickly viewing UI)
npm run build          # tsc type-check + vite build (frontend output to dist/)
npm run tauri build    # Package the desktop app

# Tests (pure functions, no GUI / Tauri needed, using Node's built-in test)
npm test               # every tests/**/*.test.ts
node --experimental-strip-types tests/layout-tree.test.ts   # or a single file

npm run typecheck      # tsc --noEmit
npm run lint           # eslint .
cd src-tauri && cargo test   # Rust-side pure helpers (path safety, hook merge, diff)
```

`tsconfig.json` enables `strict`, `noUnusedLocals`, and `noUnusedParameters`. `eslint.config.js` ignores `.claude/` — parallel-development git worktrees live there and are full copies of the repo, outside this project's tsconfig.

## Architecture: Layers and Data Flow

### Three layers

1. **Rust backend** (`src-tauri/src/`) — exposes capabilities to the frontend via `#[tauri::command]`. All registered in `lib.rs`'s `invoke_handler`.
   - `pty.rs` — one PTY per session (`portable-pty`). `pty_spawn` takes an invoke `Channel` and starts a reader thread that streams output to the frontend as raw bytes over that channel (ordered, no base64/JSON); emits `pty://exit/<id>` on exit.
   - `config.rs` — reads `agents.json` from the app config dir; writes a template with a demo launcher if it doesn't exist.

2. **IPC wrapper layer** (`src/ipc/`) — wraps Rust commands / events as TS functions. `pty.ts`'s `ptySpawn(options, onOutput)` wires the output channel (bytes arrive as `Uint8Array`); `notify.ts` handles desktop notifications.

3. **React frontend** (`src/`) — UI + state (Zustand) + agent detection logic.

### Data flow (the core of agent awareness)

PTY output → `Terminal.tsx` writes to xterm and triggers two debounced pipelines (see `App.tsx`):

- **`onScan`** (debounced 150ms for visible panes / 1000ms for hidden ones, reads the rendered text of xterm's **visible viewport**) → `handleScan` → `deriveState` derives agent state → updates the session store → on `waiting`, pops up `ApprovalPanel` + desktop notification. Also extracts cost/tokens (`extractUsageFromText`) and file changes (`extractFilesFromText`) from the viewport — alt-screen TUIs (Claude Code 2.1+) repaint via cursor positioning with almost no newlines, so the stream path never sees their footer or `⏺ Update(...)` lines; re-scanning the same lines is idempotent (`addChangedFile` dedups by path). Deliberately reads only the visible viewport, not scrollback (a prompt that was answered and scrolled away should no longer count as an active approval).
- **`onStream`** (raw decoded output, line by line) → `handleStream` → `extractFromLine` extracts cost/token/file changes → updates the store → `ChangedFilesPanel`. Partial lines across chunks are buffered by `lineBuffers` in `App.tsx`. Still effective for plain line-oriented agent output (generic profile, user-supplied profiles).
- **Changed files carry provenance** (`ChangedFile` in `agents/extract.ts`): hook-sourced entries are tagged `source: "hook"` and carry the hook payload's `cwd` (the agent CLI's live working directory for that tool call), while viewport-regex entries are `source: "scan"` and may be a bare basename or terminal-truncated. `store/changedFiles.ts`'s pure `mergeChangedFile` dedups across the two paths (an absolute hook path upgrades an earlier relative sighting of the same basename, in place; provenance never downgrades) and caps the list. Clicking a row opens the read-only diff overlay: pure `resolveDiffBase` (`src/diff/diffTarget.ts`) picks the git anchor — the entry's own absolute path first, since `session.cwd` is a creation-time snapshot that goes stale as soon as the user `cd`s — then the async Rust `git_diff_file` (`src-tauri/src/git.rs`, read-only: only `rev-parse`/`diff`/`status`, untracked files get a synthesized patch rather than `git add -N`, and `--no-ext-diff --no-textconv` stop a repo-local diff filter from executing arbitrary programs) returns a status union plus a capped patch, which pure `parseUnifiedDiff` renders.
- **`onTitle`** (xterm `onTitleChange` — the OSC 0/2 title the CLI sets itself) → `handleTitle` → `deriveTitleSignal` maps the title to a coarse busy/rest signal via per-profile `title` patterns (Claude Code and Codex both prefix a braille spinner char U+2800–U+28FF while working; Claude Code shows `✳` at rest). The signal is stored in `scanState` (busy carries a 3s TTL so a killed agent's stale spinner title can't pin the light) and consumed by the next `handleScan` as `deriveState`'s third argument, where it only **reclassifies**: scan-derived `waiting` always wins (titles cannot distinguish an approval menu from idle), busy vetoes false done/error and defaults to thinking, rest vetoes leftover thinking/tool transcript text. The title also feeds the session's sidebar name via `setTitle`, but an explicit rename (sidebar double-click / `F2` / `r`, or `Ctrl+A r`) sets `titleLocked` and the pure `shouldAcceptAutoTitle` (`store/sessionTitle.ts`) then makes that path a no-op — necessary because Claude Code rewrites the title on every spinner tick. Clearing the name unlocks it again. The `setTitleSignal` half must keep running unconditionally: it feeds state detection, not the label.
- **Hook events (primary signal when installed)** — Rust `hookserver.rs` listens on a random 127.0.0.1 port; `pty_spawn` injects `HELM_SESSION_ID` / `HELM_EVENT_PORT` into every PTY, and CLI hook processes (which inherit the CLI's env) POST their stdin JSON back (`/hook?session=<id>&source=<cli>`) → `agent://hook` event → `handleHookEvent` in `App.tsx` (normalization is a pure function in `src/agents/hookEvents.ts`, node-tested). Claude Code and Codex hooks share the same payload shape: `PermissionRequest` → waiting with an exact `tool_name: tool_input` prompt (scans confirm but never overwrite a hook-sourced prompt; a 2s grace in `scanState.markHookWaiting` stops the scan-clear path from killing the waiting state before the dialog repaints), `Stop` → done, `PostToolUse` → changed files, Claude Code statusline JSON → cost/context. Codex additionally emits OSC 9 desktop-notification sequences (`tui.notifications`; requires `notification_method = "osc9"` + `notification_condition = "always"` in config.toml) parsed via xterm's `registerOscHandler(9)` → `handleNotify` → per-profile `notify.waiting` pattern. One-click install lives in SettingsDialog's "Agent integrations" section (Rust `integrations.rs` idempotently merges marked entries into `~/.claude/settings.json`; the statusline command path is written **quoted** — Claude Code runs it through a shell and macOS's config dir contains a space ("Application Support"); reinstalling rewrites an existing helm entry to repair old unquoted installs; Codex TOML is never auto-edited, only a copyable snippet). The viewport regex pipeline above stays intact as the fallback for uninstalled hooks, older CLIs, and custom profiles.
- **Notification pipeline (single route for all alerts)** — every signal source above converges in `sessions.ts`'s `setAgentState`; `detectAgentEvent` (`store/notificationRouter.ts`, pure, node-tested) turns state-transition **edges** into alert events: entering waiting → approval/question/plan, busy (thinking/tool/waiting) → done/error (`undefined → done` deliberately doesn't fire — leftover transcript at agent detection). Two kinds are **not** edge-derived, because their whole point is that no transition happens: `interrupted` (the PTY died while the agent was working — `markInterrupted`, called from `Pane`'s `onExit` in `App.tsx` **before** `clearApproval` because it reads the pre-death `agentState`; deliberately on `onExit` rather than unmount, so closing a pane yourself never fires it) and `stalled` (busy but silent past `STALE_BUSY_THRESHOLD_MS` — the polled watchdog in `store/staleBusyWatch.ts`, the one signal source in the app that has to poll, with `store/staleBusy.ts` holding the pure judgement). Both matter because silence and progress look identical on screen, which is exactly the "waiting for a notification that will never arrive" failure. `isBusyState` (`notificationRouter.ts`) is the single definition of "the agent is working" shared by all three call sites. Each event is (1) always recorded in the **notification center** (`store/notificationCenter.ts` pure list ops + `store/notifications.ts` Zustand store; bell + unread badge in Toolbar, panel in `src/components/NotificationCenter/`; capped at 50, in-memory only; waiting entries are auto-resolved when the prompt is answered/cleared) and (2) forwarded to a desktop notification only through the single gate `shouldDesktopNotify`: settings master toggle && per-kind toggle (looked up through the exhaustive `NOTIFY_TOGGLE_KEYS` table in `sessions.ts`, so a new `NotifyKind` fails to compile instead of silently inheriting a fallback) → focus suppression (waiting/error/interrupted/stalled: focused **and** the session's pane visible on screen — active split group member or the active session itself; done: focused at all; the `notifyHiddenPanes` settings toggle, default on, reverts waiting to the old workspace-based rule and error to focused-at-all when disabled) → per session+kind 120s content dedupe (suppression is checked before recording so the blur listener in `App.tsx` can still re-fire pending prompts). Explicit approval responses call `clearNotifyDedupe` so an identical new prompt notifies immediately.

### Agent profile system (data-driven, not tied to any specific tool)

`src/agents/` — profiles use **regex source strings** (not RegExp objects) to describe how to recognize an agent and each of its states. This lets the same schema live both in the built-in TS (`builtins.ts`) and be supplied by the user's `agents.json`, merged in `registry.ts` (user entries with the same id override built-ins; launchers are appended). Therefore, **to support a new CLI agent, prefer editing the patterns in `builtins.ts` rather than writing hardcoded detection logic**.

- `types.ts` — `AgentProfile` (states patterns, extractors, detectOutput, approve/reject keys), `AgentLauncher`, `AgentConfig`.
- `engine.ts` — `deriveState` (state priority: waiting > error > tool > thinking > done) and `stripAnsi` (pure functions, tested).
- `extract.ts` — line-by-line extraction of structured info (pure functions, tested).
- `builtins.ts` — built-in `claude-code` / `codex` / `generic` profiles, with patterns calibrated to actual TUI output.

### Split groups (tmux window/pane-style)

There is no global single/split view mode. Layout is per **split group**: splitting session A (`layout:split-right/down`) creates a new session B and forms/extends a group tree containing both. Activating any member of a group shows the whole group's split layout (that session's pane focused); a session in no group renders alone at 100%. New sessions (`session:new`, sidebar `+`) are always ungrouped — only splitting creates group membership.

- `store/layoutTree.ts` — **pure-function** binary split-tree operations (split / remove / setRatio / computeLayout / findTreeBySession, etc.), with no React/Zustand dependency, directly unit-testable. Core invariant: a session appears in at most one group tree, and all sessions of a group share a workspace.
- `store/layout.ts` — wraps the above pure functions in a Zustand store holding **one tree per group** (`trees: Record<groupId, LayoutNode>`, group ids are generated UUIDs; a group always has ≥2 leaves — when removal collapses it to one leaf the group is dissolved and the survivor returns to fullscreen). `removeSession` / `setRatio` search all trees (ids are globally unique); `groupTreeOf(trees, sessionId)` resolves the tree a session belongs to. `moveSessionToWorkspace` evicts the session from its group (preserving the same-workspace invariant).
- The layout tree **only computes geometry** (each leaf's percentage rect); `App.tsx` renders all panes tiled but computes rects only from the **active session's group** tree — the ungrouped active session gets a synthetic full rect (`data-solo` removes the border; the pane label with split/close buttons shows on every pane); every other session gets no rect and is hidden via `data-in-layout="false"` CSS — so **the same set of Terminals stays mounted and is never rebuilt** (PTYs keep running, scrollback preserved). Clicking a session in the sidebar simply switches to its layout (group or fullscreen); there is no swap-into-focused-pane behavior.

### Sidebar hierarchy (workspace → session)

The sidebar (`src/components/SessionSidebar/`) is two-level: collapsible **workspaces** (visual grouping, plus an optional default folder) containing **sessions**. `store/workspaceGroups.ts` holds the pure grouping helpers (`groupSessions`, `resolveFocusedWorkspace`, `sessionsInWorkspace`, workspace file aggregation, `flattenGroupedIds`; unit-tested); `store/workspaces.ts` is the Zustand store (create / rename / delete / collapse / set default folder). A workspace can carry an optional `folder` (chosen via the header's 📁 button, native picker in `src/ipc/dialog.ts`); it is snapshotted onto each new session's `cwd` at creation (`folderForWorkspace` in `src/commands/actions.ts`) and passed to that session's PTY as the working directory — stable for the session's life, so moving it between workspaces never respawns it. A session with no workspace folder falls back to the global `settings.defaultCwd`. New sessions land in the active session's workspace; deleting a workspace also closes every session in it (the default workspace, id `"default"`, is never deletable). Sessions are dragged between workspaces via HTML5 DnD (`text/plain` carries the session id). Session cycling (`session:next/prev`, Cmd+1..9) follows the sidebar's grouped visual order (see `sessionIdsInSidebarOrder` in `src/commands/actions.ts`). The **focused workspace** is derived, not stored: it is the active session's workspace (`resolveFocusedWorkspace`). ApprovalPanel, ChangedFilesPanel (grouped by session), the Toolbar's changed-file count, and the approve/reject-all commands are all scoped to it; other workspaces surface waiting sessions (approval/question/plan alike) via a clickable badge on their sidebar header (desktop notifications stay global). The Toolbar's plan-usage meters read the **account-level** `accountPlanUsage` in `sessions.ts` (latest statusline `rate_limits` from any session; shown whenever known, regardless of the active session). The Toolbar's left side is a global fleet-status strip (`store/fleet.ts` pure helpers, node-tested): per-state chips (busy = thinking+tool, waiting, error, done; nonzero only) whose click jumps to the next session in that state in sidebar order (`activateNextInFleetState` in `src/commands/actions.ts`).

### Zustand stores (`src/store/`)

`sessions.ts` (session list + agent state; the convergence point of agent awareness), `notifications.ts` / `notificationCenter.ts` / `notificationRouter.ts` (unified alert pipeline, see "Notification pipeline" above), `workspaces.ts` / `workspaceGroups.ts` (sidebar grouping), `layout.ts` / `layoutTree.ts` (split groups), `sessionSnapshot.ts` / `sessionSnapshotSchema.ts` (restore-on-launch), `eventJournal.ts` / `journalFormat.ts` (notification history), `staleBusy.ts` / `staleBusyWatch.ts` (stall watchdog), `agentIdentity.ts` (append-only agent session ids — no removal API on purpose, see the file header) / `resumeState.ts` (in-memory resume attempts and failed ids), `theme.ts` (includes xterm themes), `ui.ts` (panel open/close state), `prefix.ts` (Ctrl+A prefix armed state + auto-disarm timer).

## Important Notes

- **Windows support**: PTYs use ConPTY via `portable-pty`. The default shell is resolved in `pty.rs` as `HELM_SHELL` → `SHELL` → platform default (Windows: `pwsh.exe` if on PATH else `powershell.exe`, launched with `-NoLogo`; Unix: `/bin/zsh`). Home falls back `HOME` → `USERPROFILE`. The `agents.json` template in `config.rs` has per-platform demo commands (`#[cfg(windows)]` = PowerShell syntax).
- **Keyboard input is four layers, each with one rule.** Adding or changing a binding means picking a layer and obeying its rule; violations are what made the old system feel inconsistent.
  1. **Global layer** — `Ctrl+A <key>` tmux-style sequences, plus the single direct binding `Ctrl/⌘+Shift+P`. The pure state machine + `PREFIX_TABLE` live in `src/commands/prefix.ts` (node-tested); `App.tsx`'s capture-phase DOM `keydown` drives it ahead of xterm and **swallows the armed second key whether or not it matches** (tmux behavior; Esc / 3s timeout / window blur disarm). Ctrl on the second key means "the bigger variant": `Ctrl+arrow` resizes where a bare arrow moves focus, `Ctrl+A Ctrl+y`/`Ctrl+n` approve/reject the whole workspace where `y`/`N` handle the active session. **Arming is suppressed while focus is in a real text field** (`isTextEntry` in `src/commands/keyTarget.ts` — the xterm helper textarea is deliberately excluded), so Ctrl+A stays select-all in the rename box, palette search and settings fields. While armed, the `WhichKey` overlay (`src/components/WhichKey/`) lists available second keys, dimming disabled commands. `KEYMAP` (`src/commands/keymap.ts`) keeps only ⌘⇧P (macOS WKWebView swallows some plain Cmd+letter combos, so any new direct binding must be verified to reach the DOM).
  2. **Region layer** — bare keys acting on whatever row/item has focus: the sidebar tree (`SIDEBAR_TABLE` in `src/components/SessionSidebar/sidebarKeymap.ts`), the changed-files list, the notification list, the launcher menu. Rule: **bare keys only** — `hasNonShiftModifier` (`src/focus/listNav.ts`) makes every handler bail when Ctrl/Alt/Meta is held (Shift stays allowed; some keys encode it in the character). Shared vocabulary: `j/k/↑/↓` move, `g/G/Home/End` jump, `Enter/Space` activate, `r/F2` rename, `Delete/Backspace/x` remove, `Escape` back to the terminal. Sidebar letters intentionally mirror the global layer (`c`/`w`/`x`/`r` = the same actions as `Ctrl+A c`/`w`/`x`/`r`); `f` (folder) and `g`/`G` (list nav) are region-local vocabulary and differ from `Ctrl+A f`/`Ctrl+A g` by design. A **pending inline confirmation captures the next key**: Enter/Space confirm, Escape cancels, anything else cancels *and is swallowed* — the same swallow rule as the armed prefix.
  3. **Modal layer** — palette / settings / diff / shortcuts help / launcher menu. Rule: `Escape` goes through `handleDismissKey` (`src/focus/focusUtils.ts`), which always `preventDefault` + `stopPropagation` and hands off to a close that restores focus to the opener (or the terminal); `Tab` is trapped by `trapTabKey`. Deliberately kept as-is: rename inputs commit on Enter/blur and abandon on Escape (standard file-manager behavior), and an unmatched second key cancels the prefix rather than falling through to `KEYMAP`.
  4. **Terminal layer** — everything else reaches the PTY untouched; the only exceptions are `Ctrl+/` (sends 0x1F) and `Ctrl+C` *with a selection* (copies), both in `Terminal.tsx`.
  `REGION_ORDER` (`focusUtils.ts`) drives `Ctrl+A Tab` and must list every `data-focus-region` in the markup. The native menu (`lib.rs`) is a mouse/discoverability entry point: items carry `(Ctrl+A x)` hints in their labels, only the palette keeps a real accelerator, and clicks emit `app://shortcut` (any id containing `:`) into the same `runCommand`.
- **The shortcut reference is generated, not written.** `src/commands/shortcutDocs.ts` (pure) builds it from `PREFIX_TABLE` + `KEYMAP` + `SIDEBAR_TABLE`, mapping each command id to the same `command.*` i18n key the registry uses so wording lives once. It feeds the in-app `ShortcutsHelp` dialog (`Ctrl+A ?`, the sidebar `?` button, Help menu) and — via `npm run docs:shortcuts` — the marked block in `README.md`. `tests/shortcut-docs.test.ts` fails if a binding is undocumented, an i18n key is missing in either language, the README block is stale, or a `lib.rs` menu hint disagrees with `prefixLabel`. Only the "Panels and overlays" / "Terminal" sections are hand-written (no table to read from), and they live in that one file.
- To add a shortcut: registry command + `PREFIX_TABLE` entry (+ `COMMAND_TITLE_KEYS` mapping in `shortcutDocs.ts`, + menu item with label hint when useful), then `npm run docs:shortcuts`.
- **What persists across launches, and the one line that governs it.** Helm persists *durable workspace state* and never pretends to revive a process: layout, cwd, titles, agent identity and a scrollback snapshot are ours to restore; the agent conversation is restored only by the CLI's own resume command; a restored pane always gets a **fresh PTY** and says so (the `restored` badge in `PaneLabel`). "Looks restored but isn't" is the failure mode this split exists to avoid.
  - **Workspaces** → localStorage `helm.workspaces`, write-through on every mutation (`workspaces.ts`, validated on load by the pure `normalizeWorkspaces` in `workspaceGroups.ts`, which also guarantees the `"default"` entry exists — the sidebar derives "deletable" from its absence). Workspace names come from `nextWorkspaceName`, derived from the existing list rather than a module counter, so numbering survives a restart; session titles now do the same via `nextSessionTitle` (`sessionTitle.ts`) — a module counter would hand out `Session 1` again right after restoring three sessions.
  - **Sessions + split layout** → `sessions.json` in the app **data** dir via the generic Rust file store (`appstore.rs`: `app_data_dir`, tmp+rename atomic replace, filename allow-list; wrapped by `ipc/appStore.ts`). Format, validation and the invariant repairs are pure functions in `store/sessionSnapshotSchema.ts` (node-tested); `store/sessionSnapshot.ts` owns only I/O timing (subscribe + 800ms debounce with a 5s cap, window blur, `onCloseRequested`; **never** a synchronous write inside a store setter, which runs at PTY-output frequency). Deliberately **not** persisted, mirroring the comment in `sessions.ts`: cost/tokens/changedFiles and `agentState`/`pendingApproval`/`pendingPrompt` — so a ghost "waiting" prompt is structurally unable to survive a restart. `launchCommand` is stored as `lastLaunchCommand` and **not** written back on restore (writing it back would silently re-run the agent); the exception is the opt-in `resumeAgentsOnLaunch`, which puts a *resume* command there before the pane mounts so it inherits `Terminal.tsx`'s `if (launchCommand && launched)` guard. `version` mismatch or malformed JSON → discard the whole file and cold-start; never migrate. Layout persists as an array of node-id-less trees, and group/node ids are regenerated on restore, which makes duplicate-id corruption unrepresentable — but **session ids are never regenerated** (an id is also the PTY key, `HELM_SESSION_ID`, and the hook-routing key).
  - **Scrollback** → one plain-text file per session (`scrollback-<id>.txt`), captured from `buffer.normal` only (the alternate screen is a half-drawn TUI frame the CLI alone can rebuild) and stored as **rendered text, not `addon-serialize` output** — Helm has live OSC 9 / 52 / 0-2 handlers, so replaying control sequences would fire desktop notifications and clipboard writes. Replay is a bare `term.write` before `spawnPty`, so it cannot reach `onScan`/`onStream`; it returns a **scan floor** consumed by the pure `scanRows` (`components/Terminal/scanRows.ts`). That floor must stay guarded by `buffer.type === "normal"`: an agent entering the alternate screen resets `baseY` to 0, and applying the floor there would kill that pane's agent detection permanently.
  - **Notification history** → `events.jsonl` (append-only, `store/journalFormat.ts` pure + `store/eventJournal.ts` I/O), read back into the notification center at boot as already-read entries.
  - **Bootstrap** runs once per app lifetime (the `bootstrapped` flag in `App.tsx`): `initRegistry()` must come first (a restored agent pane needs its profile), then `restoreFromSnapshot()`, and only if that returns false does `newSession()` create the single fresh session. Note that `getCurrentWindow()` and `invoke` **throw synchronously** without a Tauri runtime rather than returning a rejecting promise, so anything touching them is `try/catch`-wrapped and ordered after session creation — otherwise browser-only `npm run dev` starts with no session at all.
  - A persisted folder can be gone by the next launch (unmounted volume, moved project); `store/folderStatus.ts` probes it via the Rust `dir_exists` command and the sidebar strikes the path through rather than dropping it, while `Terminal.tsx` falls back to `$HOME` and — importantly — skips `launchCommand` on that path so an agent never silently starts against the wrong repo. Restore probes every restored `cwd` the same way. The other cross-launch state is user preferences in localStorage (theme, language, fonts, notifications, background, restore toggles).
- **Launching an agent** works by writing the command as user input into the PTY (`ptyWrite(id, "claude\r")`), preserving the full shell environment, rather than spawning the command directly.
- After adding a Rust command, remember to register it in `lib.rs`'s `generate_handler!` and add a corresponding wrapper in `src/ipc/`.
